# CPU 视觉编码实现与后续验证

[文档目录](README.md)

> 状态：CPU 视觉已接入；设计目标、后续路线和历史测试在下文分别说明。历史 KV 容量不代表当前引擎容量，现行策略见 [LLM 配置](LLM_MODES.md)。

目标：图片作为偶发视觉参考，允许等待，不为速度默认压缩到300–1024图片token；保留模型原生预处理和必要的细节，仅遵循模型支持上限与请求资源预算。长上下文和高并发模式共享独立CPU视觉服务。图片编码器的权重、激活和计算在CPU，GPU执行语言模型；默认使用medium思考。当前长上下文与八路65K入口均已接入CPU视觉；GPU仍保留像素暂存、图像特征缓冲及上下文KV，KV格式保持原配置。

## 依据与限制

Strata的strata-vision使用llama.cpp mtmd，是独立CPU编码器。其Flash-Next模型、mmproj文件及embedding不能直接套用本机27B Dense模型，必须匹配本机checkpoint。它公开的参考是8线程约3秒/300图片token，1024图片token的AVX2案例约8–10秒；不代表双Xeon本机性能。当前Paiton的PAITON_HOST_VISION原型将视觉块放在主存、逐层拷到GPU，仍在GPU计算，上游也未对其稳定性作资格验证；不是本方案。

## 已实现路径

运行时为`local-ai/pation-qwen38-cpu-vision:20261013-r2`。`.workbench/runtime/cpu-vision/server.py`在无GPU设备的独立容器`ai-vision-cpu`中加载原检查点的333个视觉权重张量，共460,730,096参数，使用HF原生视觉模型CPU SDPA/FP32计算并返回BF16特征。43个线程绑定CPU 0–42，容器内存上限8 GiB，特征LRU上限1 GiB；重启策略unless-stopped。服务仅监听127.0.0.1:18984。

GPU客户端把vLLM原视觉塔替换为无参数代理，保持原vLLM图像预处理、网格、图片位置编码、特征合并及语言模型路径；不以文字描述替代图片。目前输入像素沿用vLLM的GPU暂存路径后送CPU，最终特征也需要GPU缓冲，所以不是零GPU多模态占用。

只有`EncoderRunner.profile_encoder_cache`的虚构启动输入进入明确的profile上下文，以零特征分配对应GPU缓冲；不会调用CPU编码器。真实图片不进入该上下文，仍完整编码。此优化避免启动时对虚构4K图执行昂贵CPU计算，并非降采样或跳过用户图片。

CPU服务成功后，控制器才启动GPU客户端。当前高并发保留8,859,648,000 bytes KV预算，长模式保留8 GiB KV；均默认medium。特征缓存、CPU服务管理和运行时配置位于`.workbench/runtime/cpu-vision/`及`.workbench/runtime/rocm101/active.json`。

## 设计依据与后续工作

1. 从同一checkpoint提取视觉编码器与所有merger/projector，建立CPU后端；匹配原模型视觉权重，以现有GPU视觉输出为正确性基准。精度不是此次改造目标，不因迁到主存自行提高精度；根据AVX2后端支持选择计算类型，输出按原语言模型接口要求转换。
2. 保持图像预处理、patch排序、deepstack特征（若模型需要）、image_grid_thw和多轴位置编码与原GPU路径一致。CPU直接产出特征，不能以图片文字描述替代。
3. 已在vLLM视觉塔内部接入CPU服务，保持原多模态协议；GPU视觉权重完全不加载，但仍保留图像特征缓冲。
4. 按预处理像素和网格的哈希缓存特征，CPU服务固定加载同一检查点、重启清空缓存。当前CPU编码发生在vLLM多模态阶段，仍占对应GPU请求租约；后续可研究提前编码，以减少长图对生成批次的阻塞。
5. NUMA起始方案是每个CPU插槽一个worker，各8–12物理线程、本地内存，先限制2个并发编码任务，其他排队。八路生成不要求八个CPU编码器同时运行。根据吞吐测试调整，不预先开满全部超线程。
6. 首轮测试300/1024/约8100图片token，覆盖小图、4K截图、图表、细字OCR；比较特征误差、回答准确性、编码延迟、TTFT、CPU内存与整卡VRAM峰值。

## 预算与验收

预期释放视觉权重约0.88 GiB以及GPU视觉计算的激活/工作区，但不能将此前2.42 GiB预设差额全部当作已释放显存；必须重新测量启动峰值和负载峰值。图像特征在GPU上的输入缓冲及其语言模型KV仍然存在，CPU编码不消除图片上下文占用。

接入实验使用原八路纯文本8.25 GiB KV预算。该轮393,216 token参考容量仍不够八个满65K，恢复视觉预算不等于524,288总容量；当前容量以实际引擎启动结果为准。显卡同时驱动屏幕，应以整卡实际余量及无KFD驱逐/桌面故障为验收条件。

验收目标：纯文本无视觉常驻分配；图文语义与GPU基准一致；重复图片命中缓存；多轮混合八路请求不发生OOM/驱逐，CPU线程无过度竞争。500总吞吐不作为已达到结论。

参考：[Strata视觉文档](https://github.com/Niko1221/Strata/blob/main/docs/DETAILS.md#images-vision)；本地原型：engines/shared/paiton/upstream/paiton_vllm_plugin/_vendor/qwen38/paiton_host_vision.py。

## 历史接入与负载验证（2026-10-13）

- CPU真实测试图128图片token首次编码约2.34秒，缓存命中约10毫秒；CPU服务空闲约2.3 GiB，曾进行虚构4K编码时约4 GiB，完整4K真实请求耗时尚未验收。
- 与原检查点HF GPU eager BF16视觉参考的特征平均余弦相似度0.9998859，最小0.9977939，相对L2误差0.01838；不是逐位相同，也不是完整视觉准确率评测。GPU标准SDPA参考曾遇ROCm视觉头形状错误，GPU对照改用eager，生产CPU路径未改变。
- 实验八路模型加载GPU占用15.89 GiB，此前GPU视觉16.77 GiB，差约0.88 GiB；启动共享KV容量393,216 token，此前GPU视觉预设278,050 token。
- 平台八路短请求混合（6文本+2图片）全部完成，峰值8活动租约；图片正确识别三个红色正方形和一个蓝色圆形。
- 自动切换长上下文入口后，真实图片请求也正确完成；切换及冷启动约298秒，实际请求约0.92秒。此项仅验证长模式接入，不代表满256K负载验证。
- 持续输出测试发现预热请求释放租约与新请求获取租约之间存在竞争，可能残留槽位记录，使八路实际仅七路；已修复并增加复现回归测试。
