# LLM 上下文与并发配置

[文档目录](README.md) · [API 参考](CURRENT_API.md)

## 配置与应用

统一入口：`http://127.0.0.1:18982/v1`，面板：`http://127.0.0.1:13000`。

W3A4 后端按已保存的每路上下文和并发上限启动，默认 KV 预算为：64K 及以下 8,859,648,000 字节（约 8.251 GiB），更长上下文为 8 GiB。面板可自定义 Eager 与 KV 预算。主模型输出头使用 BF16，embedding 保持系统内存。

调整上下文、并发、Eager 或 KV 预算后，网关暂停接收新推理请求，等待已接收任务结束，再停止旧引擎、按新参数加载并核验。加载成功后持久化新设置并恢复请求；切换会清空旧引擎缓存。BF16 只恢复主模型输出头的数值精度，主干仍为 W3A4，尚未验证整体质量提升。

| 面板预设 | 每路总上下文 | 并发上限 | 同时满载需求 |
|---|---:|---:|---:|
| 长上下文 | 262,144 | 1 | 262,144 |
| 双路任务 | 196,608 | 2 | 393,216 |
| 均衡并发 | 131,072 | 3 | 393,216 |
| 多路任务 | 65,536 | 6 | 393,216 |
| 八路并发 | 65,536 | 8 | 524,288 |

每路额度包含聊天格式、输入、图片 token、思考和回答。上下文可自定义为 1K 至 256K，并发为 1 至 8。容量不足的配置可以保存；启动后若同时满上下文需求超过实测 KV 容量，面板显示 token 缺口；并发上限不保证所有请求同时跑满上下文。

## 容量与请求排队

余量按当前引擎启动日志的 `GPU KV cache size` 实测 token 容量减去每路额度乘以并发计算，不能从 8 GiB 直接换算。选择与当前引擎不同的上下文或并发后，显示待启动测量，不沿用旧引擎容量判断新方案。KV 实际分配读取当前容器启动参数；省略自定义预算时，64K 及以下使用官方基准的约 8.251 GiB，更长上下文使用 8 GiB。实时 KV 剩余依据引擎指标另行显示，缺少指标时显示未知。固定 KV 不包含模型权重、计算临时空间和桌面显存，也不保证任意请求不会发生显存不足。

历史容量不用于新启动引擎的预算。所有上下文统一采用 `long-kv4`、前缀缓存和 `Mamba align`，GDN 状态使用 eager（与执行模式的 Eager 开关独立），保留 DFlash。64K 及以下使用 4096 最大批处理 token、不限制长预填充；更长上下文使用 512-token 长预填充阈值和 1024 最大批处理 token。网关核验实际前缀缓存、Mamba 模式和 GDN 状态，避免重用关闭缓存的旧引擎。图捕获最大 token 数按并发乘以每轮草稿加验证 token 数收缩。未启用 CPU KV 卸载。CPU 视觉保持独立运行，GPU 接收图片特征并执行语言模型；见 [CPU视觉实现](CPU_VISION_DESIGN.md)。

配置切换等待已有请求及队列结束，期间新请求返回 409。重启完成后，新请求采用新引擎的上下文额度。网关先调用内部工作进程的 `/tokenize` 计算输入，超出单路额度返回 400；输入加输出预留超过引擎总 KV 容量也返回 400。各请求按输入 token 加最大输出量保守预留共享缓存，名额或容量暂时不足时排队，完成后释放预留。已有请求不会因调节滑块被取消。

## 模型发现与思考设置

`/v1/models` 仅发布固定模型名 `qwen38-27b-w3a4`。保存面板额度后，`contextWindow`、`context_length`、`max_model_len` 和并发元数据同步更新，模型名称保持不变；未应用的调整仅供预览。旧模型别名仍路由到同一个引擎，聊天请求不会自动改动面板设置。客户端可刷新模型列表获取最新上下文长度。模型条目同时返回 `reasoning: true`、`reasoningEfforts: {off: "none", low: "low", medium: "medium", high: "high", xhigh: "xhigh"}`、`default_reasoning_effort: "medium"` 和 `compat.supportsReasoningEffort: true`。使用静态模型列表的客户端仍需自行同步这些元数据。上方常用配置支持自定义名称、上下文和并发，保存在当前浏览器中，选择并应用后才改变服务策略。

省略 `reasoning_effort` 时默认 `medium`；显式给出本机不支持的值仍返回 400。支持 none / low / medium / high / xhigh，high 映射 xhigh，none 关闭思考；`off` 视为 `none`，`minimal`/`max` 归到最近的 `low`/`xhigh`，生效值由响应头 `X-Reasoning-Effort` 回显。所有聊天入口支持图片，`/v1/models` 声明 `vision_device: cpu`。

```python
from openai import OpenAI
client = OpenAI(base_url="http://127.0.0.1:18982/v1", api_key="local")
response = client.chat.completions.create(
    model="qwen38-27b-w3a4",
    messages=[{"role": "user", "content": "解释这段代码"}],
    reasoning_effort="medium",
    max_tokens=8192,
)
```

面板通过内部 `/api/llm-mode` 保存 `{mode, context_tokens, concurrency, eager, kv_budget_bytes}`，滑块拖动只预览，点击应用才生效；设置持久化到调度器数据目录。保留 `./lab pation-model-qwen38-27b-w3a4 start w3a4` 和 `start high-concurrency` 两种兼容命令，它们读取已保存的上下文与并发配置；网关调用时显式传递所选参数。

本地模型位置编码上限为 262,144，未启用 RoPE/YaRN 扩展。重启设置不能扩展模型位置编码。基础验证及容量核对不等于满上下文、多路长期稳定性验收。

## 日志与容量预测

引擎输出默认显示独立的启动日志，切换时展示目标配置；等待旧任务期间隐藏旧引擎启动内容。启动完成后按容器 ID 保存日志，网关重启仍可恢复。启动完成后自动切换为运行日志，保留原始健康检查、推理与错误输出。预算的 token 缺口不等于整卡显存超出；整卡占用以设备实测指标为准。

ROCm 引擎启动只保留 `HIP_VISIBLE_DEVICES` 与 `ROCR_VISIBLE_DEVICES` 的设备掩码。本地启动封装移除上游传入的 `CUDA_VISIBLE_DEVICES` 弃用别名；兼容性核验要求实际运行容器不带此别名，调整在引擎重新加载后生效。

每次启动还用引擎自己的 `get_kv_cache_capacity` 函数，从实际每层缓存规格出发，按短／长模式的循环状态、预填充和 KV 预算重新分组，计算 1K 至 256K 的容量预测曲线。所有方案在应用前显示预计余量／缺口；预测包含各组每路块需求（含 Mamba、DFlash），按所选上下文的预计容量减去上下文×并发计算。曲线按启动随机 ID 校验来源；新引擎启动后重新生成并校准。预测使用当前运行时的实际规格与分配器；并发变化或新启动的规格变化仍以启动实测校准；预测不用于拒绝推理请求，也不预测整卡显存峰值。

## 预算预览与满载校准

布局矩阵覆盖 1K–256K × 1–8 路 × graph/eager，共 4,096 项。目标池块数由目标预算除以目标块字节数向下取整；容量为 `floor(目标池块数 × 上下文 / 每请求块数)`。满载需求池、配置池预算、实际分配池分别记账，同时检查池预算、token 容量和显存约束。GDN 状态与执行 Eager 分别按启动器参数规划。

显存缓冲目前仍是启动期残差；正余量标为暂估，不能表示满载已验证。日志解析的图捕获占用只用于同一配置，其他配置使用明确标注的估算。历史容量标定不作为不同 Eager 或预算配置的容量回退。负的显存估算说明预计约束缺口，不表示当前整卡已经超额。

满载校准入口：`.workbench/cache/dsh-probe/load-calibration.sh`。脚本精确分词长输入，预留持续输出，检查同时运行路数与 KV 驻留；采样记录由主进程汇总，低显存或超时中止客户端后确认引擎排空。失败、排队或驻留时间不足的结果不会标为有效满载样本。

## 历史配置与验证记录

以下容量只适用于对应日期和配置，不作为新配置的满载验收结论。

历史记录（2026-10-13，FP8 输出头及网关热更新方案，不能作为当前 BF16 重启方案容量）：412,137 token，8 GiB KV。192K × 2 或 64K × 6 满载剩余 18,921 token；64K × 8 满载缺口 112,151 token。五档切换前后容器 ID 与启动时间一致；两路 medium 回答过程中降低到单路，两个已有回答均完成（772 / 870 输出 token）。这验证热更新与基础推理，不代表满上下文压力测试通过。

2026-10-14：上下文和并发改为重启引擎生效，KV 固定 8 GiB，输出头强制 BF16。切换失败不发布新额度；下一请求按原额度重新核验并恢复引擎。当前配置需重新取得启动容量及峰值，旧方案显存数字不代表新方案稳定性。

新方案实测（2026-10-14，64K × 4 路、BF16 输出头）：KV 容量 290,785 token、剩余满载预算 28,641 token；模型加载 13.51 GiB，图捕获 1.17 GiB。公共 API 返回 391，复用同一 worker。整卡启动采样峰值 29.95 GiB，短请求后 27.99 GiB。尚未验证四路满上下文稳定性。详见 [验证报告](../workspace/reports/config-restart-20261014/SUMMARY.md)。


2026-10-16：修复长对话始终重读的问题，统一启用前缀缓存与 Mamba align。192K × 2、BF16 输出头、图捕获、8,859,648,000 字节 KV 的启动实测容量为 398,372 token。约 60K 输入首次首字 20.16 秒，重复输入 0.87 秒，命中 59,200 token；分支、续聊和两路并发的受控检查通过。该测试不代表两路 192K 满载验收。详见 [缓存验证与方案对照](../workspace/reports/prefix-cache-20261016/SUMMARY.md)。

前缀复用要求开头的 token 完全一致且缓存仍驻留。改变前段系统提示、工具定义或消息顺序会缩短命中前缀；第一次输入与模型重新加载后需要预填充。当前缓存仅保存在运行引擎内，跨引擎切换或重启会清空。启用缓存会增加状态存储和少量计算开销，不能承诺每个短请求更快。
